# 技术踩坑手册

> 每一条都是真踩过的。**在动手之前读，比出错之后再查便宜一百倍。**

## 一、言序（Yanxu）发布

| 限制 | 真相 | 应对 |
|---|---|---|
| 标题上限 | **30 字**（草稿箱口径，不是 64）。超了直接发不进去 | 写作阶段就按 30 字写，别写完再砍 |
| 正文图 | ≤1MB。超了报 `ret:10001` | 压缩到 1000KB 以内再传 |
| 封面图 | ≤2MB | 同上，双档分开算 |
| 上传通道 | **一次性**：每张图要先拿一个独立 ticket，ticket 不能复用 | 每图单独走一次上传，失败就重新取 ticket |
| 发布接口 | **异步，无查询接口**。推完只能自己去看草稿箱 | 记录 `info_id` / `publish_id` 到台账，靠人工确认 |
| 主题样式 | **微信端会清洗**。黑色曜金、magma 等主题推过去只剩素排版 | 别指望排版效果，把力气花在文字和图上 |
| 图片顺序 | 按 blocks 顺序渲染，图片与文字混排要显式指定位置 | 生成参数 JSON 时逐块确认 |

**结论**：言序是"能发进去"的通道，不是排版工具。真正的排版保障是**内联 HTML**（粘进公众号编辑器不变形）。

## 二、公众号后台编辑器（浏览器自动化，别走）

| 坑 | 现象 | 结论 |
|---|---|---|
| 标题框 / 作者框在 iframe 内 | 坐标点击不可靠，标题被反复粘进正文 | **放弃浏览器路线** |
| 富文本粘贴 | 纯文本粘进去会丢分段；HTML 粘进去可能带多余样式 | 用内联 HTML + `margin→padding`、外层 `text-align:center` |
| 保存草稿 | 频繁触发验证 / 掉登录 | 改用 API 通道（言序） |

**判断**：凡是需要"点编辑器"的动作，都优先找 API。找不到 API 再考虑浏览器，且要接受失败率。

## 三、ima 知识库入库

```
create_media(MCP) → COS 上传（普通 PUT，签名要包一层） → add_knowledge(MCP)
```

| 坑 | 真相 |
|---|---|
| 签名报 `SignatureDoesNotMatch` | **不是权限问题，是签名少包了一层**。正确算法：`StringToSign = "sha1\n" + key_time + "\n" + sha1(HttpString) + "\n"`，直接签 HttpString 必错 |
| 误判"只允许分片上传" | 曾据此改用 Node SDK，其实是签名错。改正后普通 PUT 直接 200，纯标准库就够 |
| 重名入库 | MCP **没有删除/改名接口**。用 `add_knowledge` + 同名 `file_name` + `DUPLICATE_NAME_STRATEGY_REPLACE` 原地覆盖，库内条数不变 |
| 覆盖时名字要一致 | 库里叫什么，`create_media` 的 `file_name` 就得填什么，否则不命中替换，会多出一条 |
| 凭证 | `create_media` 返回的 SecretId / SecretKey / SecurityToken 用完即删，不入库、不外传、不进版本库 |
| 解析状态 | 图片异步解析，列表里显示"解析中"是正常，不是失败 |

**入库清单（缺一不可）**：主稿 md、完整资料 md、纯文本 txt、终稿版 html、发布包 md、配图清单 md + 全部配图 jpg。

## 四、ImageGen 配图

| 坑 | 真相 | 应对 |
|---|---|---|
| 右下角水印 | 自带「AI生成 WORKBUDDY」，位置**不固定**，多数在底边往上 50–65px，少数更高 | **裁底至少 72px，高的要裁 96px**；裁完必须看图确认，别按固定值盲裁 |
| 图里带中文 | 模型渲染的中文基本是错的 | 封面不叠字，标题用平台编辑器加 |
| 体积 | 1024×1024 PNG 常 1.5–2MB，超正文限制 | 转 JPG + quality 85 压缩 |
| 生成速度 | 逐张生成，不能批量 | 先定 5 张的 prompt，再逐张出 |

## 五、文件与路径

| 坑 | 现象 | 应对 |
|---|---|---|
| 批量改名只替换文件名 | 保留前缀会拼出 `配图/raw/cover_clean.jpg` 这种不存在的路径 | 替换要连前缀一起改，改完必须跑一次 `preview` 验证 |
| 成品被当源图再压一遍 | `assets` 扫目录没用 `--check` | 源图放 `配图/raw/`，成品放 `配图/`，成品后缀统一 `_clean.jpg` |
| `--check` 反而报"没有图片" | 加了"跳过成品"逻辑后把 `_clean` 全跳过 | 核查模式优先只看成品；一个成品都没有时才退回全部图片 |
| 预览版巨大 | 内联 HTML base64 后 10MB+ | 预览版是生成物，不进版本库；`preview` 可随时重建 |
| 图片引用指向源图 | 交付件里还是带水印的图 | 交付前 grep 一遍 `配图/raw`，应当零命中 |

## 六、工具链自身

**设计原则：配置一处改、规则数据化、功能能自测、发布有总闸、决策有依据。**

| 件 | 作用 | 坑 |
|---|---|---|
| `config.json` | 唯一配置源（账号/上限/体积/后缀/路径） | 键访问一律 `CONFIG["x"]["y"]`。写成 `CONFIG["x"].y` 运行时才炸——靠 `selftest` 抓 |
| `rules/lint_rules.json` | 规则数据化，加检查项只改 JSON | 正则写在 JSON 里要双反斜杠（`\\d{11}`）；写完必跑 `selftest`，否则正则编译失败只会"静默不查" |
| `selftest` | 29 例断言（正例/反例/引用语境/配置/数学） | **改脚本或规则后不跑 = 赌命**。重构当天靠它抓出 3 个真 bug |
| `doctor` | 体检：文件/JSON/目录/凭证残留/台账与稿件是否打架/文档数字漂移 | 台账标题与最新稿件不一致会报错——这条最值钱 |
| `preflight` | 总闸：lint + 双档 + 图片引用 + 终稿 HTML + bundle 新旧 + 台账登记 | 只查机器能查的；事实/原创资质仍需人工 |
| `ledger --check` | 台账标题字数与稿件比对 | 手写台账必错（曾把 29 字写成 27 字） |

**新增一个检查项的标准动作（三步，缺一不算学会）**：
① 写进本手册 → ② 能机检的写进 `rules/lint_rules.json` → ③ 跑 `selftest`，确认新规则真的会触发（必要时补一条用例）。

**自测自己也会错**：曾把断言写成"数竖线个数 == 19"（实际 21），红了一天才发现是断言写错而非代码写错。**断言要语义化**（行尾是不是 `| 81 |`、列数是不是 6），别数分隔符。

## 七、改表结构 = 改自动化

给 `选题库.md` 加一列「分数」后，**每日自动追加新行的任务 prompt 里还是 5 列格式**，第二天会直接串列，把表格写成一堆错位的行。

**规矩**：动任何表格列 → 同时改 ① `_topic_rows` 解析 ② 所有自动化任务 prompt ③ `selftest` 里的列结构断言。**三处必须同步。**

## 八、边界（写下来备忘）

机器能给：该写哪条、缺哪一步、哪天该回填、任务书长什么样。

机器给不了：**这篇到底好不好**。

所以排序、出骨架、催账都可以自动化，但**发不发始终由人点头**。分数是决策辅助，不是判决；风险分 <5 直接否掉，不看总分。
